Auditor: read-only correctness subagent · Branch: `Developer-Prerelease` · Scope: uncommitted Developer mode feature (`src/dev-types.ts`, `src/dev-journal.ts`, `src/dev-report.ts`, `src/core.ts`, `src/main.ts`, 3 new test files, `tests/helpers/load-main.ts`, README).
Method: full source review + `git diff` comparison against the pre-feature wiring + two scratch probes importing the real modules (`~/.hermes/cache/scratch/owla-dev/probe1-report-journal-settings.ts`, `probe2-butler-seams.mts`, both all-assertions-pass) + re-run of the 3 new test files (`node --import tsx --test`: **48 tests, 48 pass, 0 fail**). ## Summary verdict

**The feature is substantially correct and meets the three core requirements.** The settings toggle gates every surface; the session export carries history, tool calls (args/result/duration) and events; the one-file diagnostics report is assembled entirely from live plugin state (verified against a real `Butler` instance with injected bridge usage, journal data, on-disk saved chats and edit backups — nothing stubbed). The recorded-promise wrapper provably does not change what the provider receives or the tool-queue serialization. Settings migration is correct and the toggle is shared across platforms as intended.

**Three medium findings** should be fixed before this is trusted as a debugging tool: (1) turns interrupted by *New chat* mid-reply or by closing the view are **never ended** and stay `ok:null / endedAt:null` ("running") forever; (2) `loss.quality.emptyReplies` **double-counts** every real empty reply; (3) the 60-calls-per-turn recording cap is smaller than the number of calls a multi-attempt turn can legitimately run (50 per attempt × up to 5+ attempts), so calls go **unrecorded exactly on the retry/escalation turns** Developer mode exists to diagnose. Plus a set of low/info findings (dead `developer-mode-disabled` and `edit-conflict` event kinds, post-rotation event attribution, pre-startTurn failures invisible, counter nuances). No critical findings; no data-loss or vault-safety issues; persistence is atomic, bounded and traversal-safe.

## Audit questions — answers

**Q2 Turn lifecycle.** `devTurn` declared before `try` (2460); `startTurn` after routing/connect (2656), so connect failures before it create no turn (nothing to end — but see DM-07). Success: `endTurn(ok:true)` (2925) before `history.push` (2927). Failure: `endTurn(ok:false)` in catch (2940). Tool-budget hard stop aborts the controller and throws `'Stopped.'` (2681-2684) → catch ends the turn. User Stop → `signal.aborted` → catch ends with `'Stopped.'`, `turn-error` suppressed for aborts (2941). Retry/escalation loops keep one turn; counters updated per iteration. **Not ended exactly once on every path:** epoch change/newChat mid-turn and view close early-return before `endTurn` (DM-01), and disabling mid-turn gates `endTurn` to a no-op. `endTurn` is idempotent — `if(!turn||turn.endedAt!==null)return` (dev-journal.ts:216), first end wins (tested + probe 1, including a post-success throw attempt: a later catch cannot flip an already-ended turn, though it can still append a `turn-error` event). `toolEnd` likewise first-outcome-wins (196). Tool calls recorded on **all** dispatch paths: pre-queue abort/epoch `'Stopped.'` (2678), guard hard (2680-2685), guard soft (2686-2689), `pluginTurn.invoke` (2692), `this.tool` (2694), repeat rejection (2695-2699) — failures via the `recorded` wrapper, successes at 2700; exceptions are the 60-cap (DM-03) and disabled journal. **Wrapper semantics:** diff replaces `toolQueue=operation.catch(()=>{}); return operation` with `recorded=operation.catch(e=>{toolEnd(…);throw e;})`, `toolQueue=recorded.catch(()=>{}); return recorded`. Probe 2 micro-model of both wirings: identical execution order, identical resolution values, identical rejection (same error object identity verified), queue survives failures, zero unhandled rejections; the only difference is one extra microtask hop before the next queued tool starts — no semantic change. When recording is off or `devCall===null`, `recorded===operation` (byte-for-byte the original behavior).

**Q3 Counters.** `history-trimmed`: `dropped=this.history.length+2-12` computed before push (2923) — probe 1 verified equality with actual `push(2)+slice(-12)` loss for every L∈[0,12] (fires only at L=11→1, L=12→2; history is always even-length, so in practice "2 older messages" each turn once full). `devAttempts=1+devEscalations+devRetries`; `devEscalations` increments exactly with `qualityEscalations` (2732-2733), `devRetries` exactly with `autoAttempts` (2787-2788) — consistent (phantom-escalation nuance: DM-08). `devTurnStartMs=turnStartMs` per attempt (2668-2669): success latency = final attempt incl. post-processing; failure latency = last started attempt → sane "latency of the final attempt" semantics per the contract (dev-types.ts:96-97). `estimatedInputTokens`: no double counting (prompt/context/replay are disjoint; context is post-trim); excludes instructions/images/wrapper and counts once per turn (DM-10).

**Q4 Chat attribution.** `startTurn` stamps `chatId` at creation; `newChat()` rotates always (even disabled, dev-journal.ts:163-164); `exportSession` filters `currentChatTurns/Events` by the current id. **A turn started in chat A can never leak into chat B's export** — probe 1 confirmed the turn keeps A's id after rotation and B's export is `null` with no B turns. Two wrinkles: the abandoned A turn stays "running" (DM-01), and events emitted for it after rotation carry B's chatId (DM-05). Neither behavior is documented in README or report notes. `openSavedChat` is blocked mid-turn (`if(this.controller)…return`, 1524) and double-rotates when idle (DM-15).

**Q5 Report correctness (probe 1, realistic synthetic input).** 2 providers with usage snapshots (Codex primary+secondary, OpenCode Go rolling), 4 turns incl. failed calls of **every** `classifyToolError` class, events of **every** kind, 2-provider routing history, saved chats. Verified: `ruleViolations` = {unoffered-tool, path-refused, title-rule, tool-budget-soft, tool-budget-hard, repeat-call}, newest-first, **no** stale-snapshot/edit-too-large/stopped/other; stale lands in `loss.data.editConflicts` (event + stale call + stale rejection = 3); `totals` deep-equal `computeDevTotals` over the **full** journal while `currentSession.events` capped at newest 300 of 500 (totals still 250/250); error strings redacted, user prompt/reply/result untouched, input not mutated; markdown ≤19 500 with all sections (3 427 chars; maximal 100-turn/6000-call journal → 4 877 chars, 20 turn lines, 20 chat lines, 10 violation lines). Classification strings match the real guard messages verbatim (tool-guard.ts:19,28; main.ts:1764,2112; opencode.ts:554; claude.ts:368; core.ts:213-214,247,250,268). One defect found: DM-02.

**Q6 Test quality.** The 48 tests assert the contract, not tautologies: ring bounds and oldest-first eviction, per-field clip caps, circular/exotic args, first-wins idempotence, chat rotation filtering, image sanitization, persistence roundtrip incl. 0600/0700 modes, corrupt/oversized/missing tolerance, malformed-entry salvage, retention eviction, path-traversal rejection (`../evil`), clear safety (non-UUID files kept), classification against real guard strings, redaction (incl. prose-preservation and idempotence), report caps/totals/redaction/no-mutation, markdown bounds, migration strictness and cross-platform sharing, onload/command/menu gating, live diagnostics section presence, session save gating + private-storage location. **Critical untested paths:** (1) `send()` itself — no test drives the turn lifecycle, so DM-01 (epoch/close early return), the wrapper in real context, and `journal.save` in `finally` are uncovered; (2) DM-02 is *cemented* by dev-report.test.ts:244 (`emptyReplies=2` asserted for fabricated independent sources — no test simulates the real same-occurrence wiring); (3) DM-03 cap-vs-per-attempt-budget interaction; (4) DM-04 disable event (toggle test asserts only the enabled event); (5) DM-05 post-rotation event attribution; (6) `history-trimmed` arithmetic and input-token composition; (7) `downloadJson`/settings `visible` rendering (DOM — legitimately unverified-live).

**Q7 Settings migration.** `developerMode` is outside `PLATFORM_SETTINGS` (core.ts:130) and outside the `modern` conditional in `migrateSettings` (core.ts:89) → applies to every schema version; `writeSettings` keeps it in the shared top level (`shared={...prefs}`, platform keys only moved to `platforms.<key>`, core.ts:141-146); `readSettings` merges `{...data,...own}` and `own` never contains the key. Probe 1 verified: legacy `{}` → false; `'true'` string → false; mac writes true → **windows reads true** (intended shared behavior) while windows keeps its own provider; a windows save preserves mac's toggle and mac's provider; toggle-off propagates; top-level `schemaVersion` lost in sync but `platforms` present → still reads true (core.ts:137 fallback). `onload` re-saves legacy data to schema 3 without dropping the toggle (main.ts:122).
